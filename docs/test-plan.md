# DoorSix 用户场景测试方案

## 1. 测试目标

本测试方案围绕 DoorSix 的真实用户使用路径设计，验证用户能否顺畅完成从打开 App、进入牌桌、理解规则、完成出牌/过牌，到查看单局结算和联机房间的核心闭环。

当前版本覆盖 Flutter 人机练习桌原型，并已根据后端接口测试报告重新开放安卓端创建/加入房间入口。多人联机测试以服务端接口、WebSocket 和 App 集成验收共同确认。

## 2. 测试范围

### 2.1 客户端范围

- 首页展示与入口跳转。
- 规则选择页展示和规则卡片进入牌桌。
- 6 人牌桌座位、队伍、当前回合、中央出牌区展示。
- 手牌选择、取消选择、整理、提示、出牌、过牌。
- 牌型识别、非法牌型和压不过提示。
- AI 自动出牌、过牌和回合推进。
- 出完名次记录和单局结算弹层。
- 创建房间、加入房间、准备、开局和服务端快照同步。
- 规则说明、牌局日志入口。
- 总战绩页占位展示。

### 2.2 服务端范围

- 健康检查。
- 创建房间、房间号查询、加入房间、离开房间。
- 玩家 token 鉴权。
- 快照、玩家战绩、房间历史接口。
- WebSocket 连接、ready、start_game、play_cards、pass、sync_state、ping。
- AI 补齐 6 人座位。
- 服务端权威发牌、出牌校验、过牌、结算、战绩日志。
- Redis 可用和不可用时的状态存储行为。

### 2.3 非本轮重点

- 完整天津/塘沽路全部地方细则。
- 账号体系、好友、公开大厅、观战、聊天、语音。
- 真实支付、排行榜、长期数据库统计。
- 正式联机房间视觉打磨、聊天、邀请分享和后台重连体验。

## 3. 用户画像与核心场景

| 用户类型 | 使用目标 | 关键关注点 |
| --- | --- | --- |
| 新手玩家 | 快速理解并试玩砸六家 | 入口清晰、规则提示可读、错误操作有反馈 |
| 熟手玩家 | 按天津基础规则顺畅打完一局 | 发牌、牌型、压牌、过牌、结算符合约定 |
| 房主玩家 | 创建房间并邀请他人 | 房间号、座位、准备、开局、断线恢复 |
| 加入玩家 | 输入房间号加入牌局 | 加入成功、座位分配、身份保持 |
| 弱网用户 | 切后台、断线后回到牌桌 | 状态可恢复，不丢手牌和回合 |

## 4. 测试环境

| 环境 | 用途 | 配置建议 |
| --- | --- | --- |
| 本地 Flutter | 客户端功能和 Widget 测试 | Flutter stable，执行 `flutter analyze`、`flutter test` |
| Android 真机 | 手势、性能、屏幕适配 | 至少覆盖低端机和主流机型 |
| Android 模拟器 | 回归测试 | 360x800、412x915、平板尺寸 |

| 远程服务 | 上线前冒烟 | `cd server && npm run test:remote` |

## 5. 测试策略

### 5.1 分层策略

- 单元测试：规则引擎、牌型识别、比较大小、发牌、排序、结算。
- Widget 测试：首页、规则选择页、牌桌关键状态、按钮可用性、结算弹层。
- 服务端接口测试：HTTP 成功/失败分支、鉴权、错误码、数据结构。
- WebSocket 集成测试：创建房间后连接、准备、开局、出牌、过牌、状态广播。
- 手工探索测试：真实用户操作手感、误触、长时间对局、不同屏幕尺寸。
- 回归测试：每次规则引擎、牌桌状态机、服务端协议变更必须跑完整自动化。

### 5.2 优先级

| 优先级 | 定义 | 示例 |
| --- | --- | --- |
| P0 | 核心闭环阻断或数据错误 | 无法进牌桌、无法出牌、结算错误、服务端泄露他人手牌 |
| P1 | 主要功能异常但有绕行 | 提示不准确、过牌状态不刷新、日志缺关键动作 |
| P2 | 体验和展示问题 | 文案不清、按钮状态不够明显、部分机型布局拥挤 |
| P3 | 优化项 | 动效细节、音效、震动、统计展示增强 |

## 7. 规则专项测试

| 编号 | 检查点 | 预期 |
| --- | --- | --- |
| RE01 | 一副牌生成 | 共 54 张，含大小王，cardId 唯一 |
| RE02 | 6 人发牌 | 每人 9 张，无重复、无遗漏 |
| RE03 | 排序 | 4 到 A、2、3、小王、大王按强度升序排列 |
| RE04 | 单张 | 任意 1 张为合法单张，单张混儿保持自身点数 |
| RE05 | 对子 | 自然对子合法，单混儿加自然牌可成对子 |
| RE06 | 三张/四张 | 同点数加混儿可成合法组合 |
| RE07 | 多自然点数 | 两个以上不同自然点数的组合非法 |
| RE08 | 全混儿组合 | 多张全为混儿时有效点数按 3 处理 |
| RE09 | 跨牌型压牌 | 四张不能压三张、对子或单张 |
| RE10 | 同牌型比较 | 只有同类型、同张数、点数更大才能压过 |
| RE11 | AI 建议 | 有目标时返回可压目标的最小组合，无目标时返回最小单张 |
| RE12 | 客户端/服务端一致性 | Dart `RuleEngine` 与 Node 服务端规则在牌型、强度、结算上保持一致 |

## 9. 自动化测试建议

## 10. 上线准入标准

版本进入可试玩/可分发前，必须满足：

- P0 用例 100% 通过。
- P1 用例通过率不低于 95%，未通过项有明确修复计划。
- `flutter analyze` 无错误。
- `flutter test` 全部通过。
- `cd server && npm test` 全部通过。
- 远程部署前 `npm run test:remote` 通过。
- 客户端不出现他人完整手牌泄露。
- 单局至少连续完成 10 局人机对局无卡死、无崩溃。
- Android 真机完成首页、规则选择、人机牌桌、联机创建/加入房间、结算全流程验收。

## 11. 风险与重点关注

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 地方规则口径差异 | 用户认为牌型或结算不对 | 所有规则事实沉淀到 JSON 和规则说明，避免隐式实现 |
| 客户端和服务端规则不一致 | 联机时客户端提示可出但服务端拒绝 | 建立共享牌例回归集 |
| AI 连续行动状态复杂 | 可能死循环或跳错玩家 | 增加固定局面状态机测试 |
| 断线重连 | 用户可能丢失牌桌状态 | 以服务端快照作为唯一事实源 |
| 手机屏幕手牌拥挤 | 误触、看不清 | 真机覆盖小屏和大屏，重点测试 9 到 18 张手牌 |
| 战绩日志损坏 | 历史统计不准 | 日志解析容错，新增坏行跳过测试 |
